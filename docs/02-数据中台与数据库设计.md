# 数据中台与数据库设计

> 版本：v1.0 ｜ 日期：2026-10-16 ｜ 状态：已确认方向（业务库 MySQL + 空间库 PostGIS）

## 一、为什么现在上数据库

权限分级、项目隔离、全模块增删改查落地后，内存模拟库的三个硬伤全部暴露：
重启丢数据、多人协作无一致性、无法审计追溯。数据中台的第一步就是把"状态"从进程内存搬到数据库。

## 二、总体分层（数据中台视角）

```
┌─────────────────────────────────────────────────────┐
│  应用层  管理平台 / GIS大屏 / 在线提取 / 解译服务     │
├─────────────────────────────────────────────────────┤
│  服务层  Spring Boot 业务服务（JPA / 权限 / 审计）    │
├──────────────┬──────────────┬───────────┬───────────┤
│ 业务库 MySQL │ 空间库 PostGIS│ 对象存储   │ 缓存 Redis │
│ 用户/角色/   │ AOI/解译结果  │ MinIO     │ 会话/令牌/│
│ 项目/站点/   │ 矿权边界/     │ 原始影像/  │ 实时状态  │
│ 任务/告警/   │ 扰动边界/     │ 结果栅格/  │           │
│ 规则/提取记录│ 传感器点位    │ 报告文件   │           │
└──────────────┴──────────────┴───────────┴───────────┘
```

**分库原则一句话**：带"几何"的进 PostGIS，其余进 MySQL，文件进 MinIO，热状态进 Redis。
判断口诀：这个字段将来要不要被"空间关系"查询（相交/包含/缓冲区）？要 → PostGIS；不要 → MySQL。

## 三、业务库设计（MySQL 8.0，库名 rs_platform）

### 3.1 表清单

| 表 | 说明 | 关键字段 |
|---|---|---|
| users | 用户 | username(uk), display_name, role_code(fk), phone, status, password_hash |
| roles | 角色（可自定义） | code(pk), name, description, builtin, page_perms(json), action_perms(json) |
| projects | 矿区项目 | name, region, status, manager, description |
| project_members | 项目成员（数据授权） | project_id, username（联合唯一） |
| stations | 监测站点档案 | project_id, station_name, station_type, work_status, device_sn, device_model, firmware, sensor_id |
| sensors | 传感器点位与最新值 | project_id, name, type, status, latest_value, unit（经纬度在空间库） |
| tasks | 解译任务 | project_id, name, algo_type, status, progress, image_name |
| alarms | 告警记录（追加型） | project_id, sensor_id, level, indicator, value, threshold, status |
| warning_rules | 预警阈值规则 | sensor_type(uk), indicator, yellow/orange/red_threshold, enabled |
| extractions | 在线提取记录（元数据） | project_id, name, class_type, satellite, year, aoi_area_ha, extract_area_ha, coverage_pct, created_by |
| audit_logs | 操作审计（预留） | username, action, target, detail, created_at |

### 3.2 设计要点

1. **角色权限存 JSON 数组**而不是关联表：权限点是平台内固定的有限集合（PermCatalog），
   JSON 足够且查询简单；权限点本身由代码目录管理，不是业务数据。
2. **项目成员独立关联表**：项目授权是高频读写、需要按人查项目列表，关联表比 JSON 合适。
3. **告警追加不删**：告警是审计证据，只允许状态流转（未确认→已确认→已解除），不给物理删除。
4. **extractions 只存元数据与统计值**，AOI 与结果多边形几何在空间库，两边用 extraction_id 关联。
5. 所有表带 created_at / updated_at；删除一律先评估"审计上能不能删"，能给状态字段就不删行。

## 四、空间库设计（PostGIS，库名 rs_geo）

| 表 | 几何类型 | 说明 |
|---|---|---|
| extraction_aoi | POLYGON | 在线提取的圈选范围，extraction_id 关联业务库 |
| extraction_features | MULTIPOLYGON | 提取结果要素集合，extraction_id 关联 |
| sensor_locations | POINT | 传感器/站点空间位置（业务库 sensors.id 关联） |
| mine_boundary | MULTIPOLYGON | 矿权/项目边界（来源、有效期、核验日期） |
| disturbance_yearly | MULTIPOLYGON | 年度实际扰动边界（实施方案核心成果层） |
| class_result | MULTIPOLYGON | 解译七类结果（任务+年份+类别三键定位） |

要点：
1. **矿权边界与实际扰动边界分表分管**——这是实施方案的红线，不能合并。
2. 统一存 WGS84（SRID 4326），面积计算时按矿区转本地投影（PostGIS 里 ::geography 直接出米制面积）。
3. 全部带 source / confidence / review_status 字段：解译结果必须区分"机器产出"与"人工核验"。

## 五、本机落地策略（无管理员权限、无 Docker）

| 组件 | 本机开发（现在） | 服务器部署（生产） |
|---|---|---|
| MySQL | 绿色版 zip，D:\Dev\mysql，端口 3306 | 官方源/Docker |
| PostGIS | **暂缓**：空间几何先以 JSON 存 MySQL，GeoStore 接口隔离 | PostgreSQL+PostGIS 容器 |
| MinIO | 暂缓，文件先落本地磁盘 data/ | MinIO 分布式 |
| Redis | 暂缓，刷新令牌/缓存用内存 | Redis |

GeoStore 抽象是本机与生产差异的唯一接触面：本机实现存 MySQL JSON，
生产实现走 PostGIS 几何类型——业务代码零改动。

## 六、数据中台演进路线

1. **现在**：MySQL 单库承载业务状态，JPA 迁移管理表结构，内存 mock 全部退役
2. **demo 演示期**：+ MinIO（影像/结果文件）、PostGIS（空间层）
3. **生产期**：+ Redis（会话/缓存/队列）、TDengine（传感器时序）、审计与备份策略

> 原则：每一步只引入"当前功能真实需要"的组件，数据中台是长出来的，不是一次堆出来的。
