## 一、平台瓶颈（Windows 本机无法完成的，只能靠外部环境）

### 1. ~~snaphu 不支持 Windows~~ → **已解决：用 ESA 官方预编译 snaphu.exe**

**原判断（2026-10-30）**：`snaphu-py` 官方 OS 标签只有 linux|macos，是纯 C 项目，要编译器；
Windows `pip install snaphu` 拿不到轮子，本机无编译器 → C 阶段（20m 解缠）卡死。

**实测结论（2026-11-02 修正）**：**不需要 Linux，也不需要编译器。**

关键发现：`snaphu-py` 是 Python 绑定（需编译），但 **SNAPHU 本身是独立 C 程序，
ESA 官方为 Windows 提供了预编译包**（MSYS2 构建，v1.4.2）：

```
https://step.esa.int/thirdparties/snaphu/1.4.2-2/snaphu-v1.4.2_win64.zip
```

下载解压即可用，里面是 `bin/snaphu.exe`（378KB）+ `msys-2.0.dll`，
**算法与 snaphu-py 完全相同**（同一份 Stanford 源码）。

| 后端 | 依赖 | 平台 | 质量 | 状态 |
|---|---|---|---|---|
| `snaphu` | snaphu-py（Python 绑定，需编译） | 仅 Linux/macOS | 工业级 network-flow | 可选 |
| **`snaphu-exe`** | **ESA 预编译 snaphu.exe** | **Windows 也可** | **工业级，同上** | **本机已启用** ✅ |
| `python` | scikit-image（cp313 轮子） | 全平台 | Herráez 2D，精度略逊 | 兜底 |

**一键安装（Windows）**：运行 `inference/scripts/setup_snaphu_windows.ps1`
（下载 ESA 官方包、解压到 `D:\Dev\snaphu`、验证可运行）。
`algorithms/unwrap.py` 的候选路径已包含该位置，也支持用环境变量 `SNAPHU_EXE` 指定别处。

**踩过的坑（已写进代码注释与测试，防止复发）**：

1. **snaphu 默认文件格式不是单通道 float32**。默认输入 `COMPLEX_DATA`（复数对）、
   输出与相关性 `ALT_LINE_DATA`（双通道：幅度+相位）。按单通道读写会得到完全错乱的结果
   —— 实测合成数据残差从 2.9mm 恶化到 **40.6mm**。修法：用配置文件显式声明
   `INFILEFORMAT` / `CORRFILEFORMAT` / `OUTFILEFORMAT` 三者为 `FLOAT_DATA`。
   `unwrap_snaphu_exe` 已固定这样做，并有跨 ±3π 的斜坡还原测试守护。

2. **电离层口径必须一致**。官方 `unwrappedPhase` 与我们的 20m 解缠路径都要减
   `ionospherePhaseScreen`（80m 网格，需插值到 20m）。口径不一致会让对比相关性
   从 0.75 掉到 0.67。实测在大范围上减电离层是**必需**的（某半幅 std 4.82 → 0.96 rad）。

**实测精度（茜坑 2026-07-21 那景，与官方 80m 产品对比）**：

| 指标 | 值 | 说明 |
|---|---|---|
| 空间相关 r | **+0.748** | 去常数偏置后 |
| 去偏置 RMS | **9.5 mm** | 官方产品自身 std 13.0 mm |
| 合成数据自检 | RMS **2.92 mm** | 已知真值，峰值 40mm |

说明：r 不到 0.9 是**分辨率差异**造成的，不是解缠错误 —— 我们解的是 20m **单视**，
官方 80m 是**多视（约 16 视）+ 滤波**的结果，噪声水平本就不同。小 AOI（5km）、
相干性 0.42 的条件下，r≈0.75 属正常水平。

**仍然建议 Linux 的场景**（性能/规模，而非可行性）：
- 整景（4000×4000+）或几十景长时序 SBAS —— 内存与耗时更适合大机器；
- Sentinel-1 干涉处理（需要 isce2，见下面第 3 条）。

**关于 `isce3`**：仍只有 Linux 轮子。但 20m 解缠只用 snaphu，不需要 isce3；
只有将来自己跑 Sentinel-1 干涉（ISCE2/MintPy 那套）才需要。

**关于 WSL**：本次执行 `wsl --install --no-distribution`，DISM 报告两个可选功能启用成功，
但需**重启系统**才生效（错误码 `WSL_E_WSL_OPTIONAL_COMPONENT_REQUIRED`）。
**既然已用 snaphu.exe 打通 Windows 路径，WSL 不再是必需项**，可以不重启。

### 2. 本机无 Docker / 无 C 编译器 / ~~无 WSL~~（WSL 已启用，待重启）

排查结果（2026-10-30 首次，2026-11-02 复查）：

| 环境 | 2026-10-30 | 2026-11-02 复查 |
|---|---|---|
| WSL | 被安全策略黑名单拦截（拒绝访问） | **可选功能已启用，待重启生效**（`WSL_E_WSL_OPTIONAL_COMPONENT_REQUIRED`） |
| Docker | 无 | 无 |
| gcc / cc / cl（C 编译器） | 无 | 无 |
| cmake / make | 无 | 无 |
| MSYS / MinGW / Cygwin | 无 | 无 |

**这些确实导致「需要编译 C/C++ 原生扩展」的 Python 包（snaphu-py、isce3）装不上**，
但**不再阻塞 20m 解缠**——用 ESA 预编译的 `snaphu.exe` 即可（见第 1 节）。

未来若引入 ISCE2、MintPy 等 InSAR 引擎，仍然需要 Linux（那类工具没有 Windows 二进制分发）。

### 3. Sentinel-1 干涉处理需要 Linux + 大内存

要拿到 Sentinel-1 的 12 年形变时序（茜坑有 837 景 SLC，2014 至今），必须自己跑干涉
（isce2 / MintPy）。这套栈：
- 依赖 Linux（isce2 无 Windows 支持）；
- 内存要求高（处理整景 SLC，建议 ≥32GB；本机 i7-4790 / 16GB 不够）；
- 处理量大（数十景配准 + 干涉 + 解缠 + 时序反演，单矿区可能数小时到数天）。

**结论**：Sentinel-1 长时序 SBAS 是「有 Linux 服务器」之后的阶段，本机做不了。

## 二、数据瓶颈（数据本身还不够，不是代码问题）

### 4. NISAR 时序太短（3 个月），出不了可信加速度

实测（茜坑矿区，track 18，8 期，2026-06 ~ 2026-10）：

- **速率**：中位 -10.5 mm/yr，量级合理，但标准差 69 mm/yr，信噪比约 0.2 —— **勉强可用**；
- **加速度**：中位 -104 mm/yr²，标准差 1024 mm/yr²，**信噪比仅 0.10** —— **完全不可用**；
- 去平面后残差/原始 = 0.94，说明空间上几乎没有可分辨的形变结构，基本是噪声。

**根因**：加速度是位移的二阶导，噪声被平方级放大。3 个月、8 期数据，单期大气/轨道残差
（几十 mm）远超真实加速度信号（每月几 mm 的变化），无法靠时间平均压掉。

**结论**：要出可信加速度和「倒数速度外推失稳时刻」，需要：
- **≥1 年时序**（等 NISAR 数据积累——NASA 称 2026 年底补完 2025-09 以来的数据，约 14 个月）；
- 或换 **Sentinel-1 的 12 年时序**（但需先解决第二节的 Linux 处理能力）。

**代码的正确处理**：`algorithms/deformation.py` 对数据不足返回 `insufficient=True`，
`run_deformation.py` 会输出 `reliable:false` 并明确标注「信噪比 < 0.3，不输出加速度与失稳判定」。
**宁可说"数据不够"，不把噪声当形变**——这是口径红线，不能为了演示好看而编数。

### 5. NISAR 幅宽边缘导致覆盖率骤降

同一矿区、不同轨道，有效像元占比可差 6 倍：

| 轨道 | 方向 | 幅宽经度范围 | 茜坑（114.87~114.93）位置 | 有效率 |
|---|---|---|---|---|
| track 140 | 升轨 | 114.57~117.76E | 贴西边缘 | **14.3%** |
| track 18 | 降轨 | 113.84~117.12E | 居中 | **84.2%** |

**结论**：**选轨道比选日期重要**。GUNW 的幅宽边缘（near/far range 两端）有大量无效像元，
矿区若贴边，掩膜会把大部分像元置 0。检索时先看轨道足迹（`stringFootprint`），
选覆盖居中的轨道。

### 6. NISAR 下载体量（磁盘与时间成本）

- 单景 GUNW 2.2~2.3 GB（含 80m 解缠 + 20m wrapped 复数 + 元数据）；
- 本机走代理下载约 2.6 MB/s，单景约 11 分钟，8 期约 1.5 小时、约 18GB；
- 缓存落在 `inference/.cache/nisar/`，已 gitignore，不进仓库。

**结论**：批量下载前先确认磁盘（本机 E 盘 244GB 余量够），演示前可预下载"预热"。

### 7. Earthdata 账号的两次前置授权

NISAR 数据免费，但要 Earthdata 账号，且首次下载前有两道「人工」关卡（代码无法代劳）：

1. **档案补填 Study Area**：否则 ASF 返回 401「application required attributes: Study Area」，
   需到 `urs.earthdata.nasa.gov` 个人档案补填研究领域；
2. **应用预授权**：访问 ASF 给的 `approve_app?client_id=...` 链接点同意，
   否则 401「Pre authorization required」。

这两步做完才拿到下载凭证。凭据放 `~/.netrc`（机器 `urs.earthdata.nasa.gov`），不入仓库。

## 三、算法瓶颈（方法本身的性质，需正确预期）

### 8. 单轨只能给 LOS 视线向，不等于垂直沉降

InSAR 天然只能测「视线向（LOS）位移」。单条轨道的结果**不能写成"垂直沉降"**。
要解出垂直 + 东西向分量，需要升降轨联合（`algorithms/deformation_fusion.py` 的
`decompose_los_to_2d` 已实现）；南北向因轨道近极地，基本不可解。

**结论**：报告和界面必须标注「LOS 视线向」，升/降轨联合前不承诺"沉降量"。

### 9. 单期干涉图有长波大气/轨道残差，必须参考区归零

实测：单期位移整体偏移可达上百 mm（track 18 中位 +160mm，折算 4.9m/yr，物理上不可能）。
这是大气/轨道残差，不是真实形变。必须选「稳定参考区」把每景减去参考区中位值
（`algorithms/sbas.py` 的 `reference_correction`）。不做这步，速率场会整体偏一个假常数。

### 10. 加速度对噪声极其敏感，是「数据够多」才能做的指标

速度是一阶导（抗噪一些），加速度是二阶导（噪声放大）。这是数学性质，不是实现问题。
工程上的正确姿态是：**先看信噪比，达标才输出加速度**，否则明说"数据不足"。

## 四、口径红线（交付合规，任何时候不能越）

这些在 `docs/24` 和既有报告里已有，形变功能新增后补充两条：

1. **形变速率/加速度是「潜在形变风险筛查」，不是边坡稳定性评价，不给安全系数**。
2. **信噪比不足时，形变结果必须标注"仅供参考"，且不参与风险提级**——否则就是把噪声当
   滑坡信号，可能造成误报警或漏报，后果比"没数据"更严重。
3. 单轨结果是 LOS 视线向，非垂直沉降；判定需结合边坡单元、现场勘察与多源数据复核。
