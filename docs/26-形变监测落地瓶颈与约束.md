# 形变监测落地瓶颈与约束说明

> 时间：2026-10-30
> 关联：`docs/24-解译服务工程结构.md`（工程分层）、`docs/25-部署方案.md`（部署）
> 性质：技术约束记录，回答「形变功能为什么有的能跑、有的要等 Linux/数据」

本文记录「地表形变监测（NISAR/Sentinel-1 InSAR → SBAS → 速度/加速度 → 安全判定）」
这条新链路在落地过程中遇到的硬瓶颈。分四类：**平台瓶颈、数据瓶颈、算法瓶颈、口径红线**。
每一条都注明「是暂时绕过、还是需要外部条件」。

---

## 一、平台瓶颈（Windows 本机无法完成的，只能靠外部环境）

### 1. snaphu / isce3 不支持 Windows —— C 阶段（20m 解缠）本机跑不了

这是最硬的一条。

- `snaphu`（SNAPHU 相位解缠器，isce-framework/snaphu-py）**官方 OS 标签只有 linux|macos**，
  是纯 C 项目，需要 CMake + C 编译器构建。Windows 上 `pip install snaphu` 拿不到轮子，
  只能下到 `snaphu-0.4.1.tar.gz` 源码包，本机没有编译器，装不上。
- `isce3`（NASA ISCE 的 Python 绑定）同样在 Windows 无预编译轮子（`pip index` 报
  `No matching distribution`）。

**结论（已部分解除，2026-10-30）**：

snaphu 本身确实只能在 Linux 跑，但 **20m 解缠不再被它卡死** ——
现在有一条纯 Python 后端，Windows 也能产出同口径结果。

| 后端 | 依赖 | 平台 | 质量 |
|---|---|---|---|
| `snaphu` | snaphu-py（纯 C，需编译器） | 仅 Linux/macOS | 工业级 network-flow，整景/长时序首选 |
| **`python`** | **scikit-image（有 cp313 轮子）** | **Windows / Linux / macOS** | 2D Herráez，AOI 几十 km² 内可用 |

**实现**：`algorithms/unwrap.py` 新增 `unwrap_python`（用 `skimage.restoration.unwrap_phase`）
与 `unwrap_auto`（有 snaphu 走 snaphu，否则自动退回 python）。
新脚本 `scripts/unwrap.py` 跨平台，一条命令出三份 GeoTIFF + 元数据：

```bash
# Windows 直接能跑（无 GUNW 时用 --synthetic 自检）
python scripts/unwrap.py --input GUNW.h5 --aoi 114.87,28.57,114.93,28.62 --out out/
python scripts/unwrap.py --synthetic --out out/
```

**关键设计**：`unwrap_phase` 支持 masked array —— 被 mask 的像元既不参与解缠、
也不影响邻域，所以低相干区（水体/植被/叠掩）不会把噪声扩散到整个 AOI。
这是能替代 snaphu 的技术前提。

**实测（合成已知形变场，峰值 -40mm）**：
- 无噪声线性场：解缠残差 **0.0000 弧度**（完全还原）
- 加 ±0.15 弧度噪声 + 低相干水块：RMS **2.92 mm**、最大 14.60 mm（相对 40mm 峰值约 7%）
- 低相干区全部 NaN，邻域无污染
- 产物：`unwrapped_phase.tif` / `los_disp_mm.tif` / `coherence.tif`（EPSG:4326、20m 像元）+ `unwrap_meta.json`

**测试**：`tests/test_unwrap_python.py` 5 个用例（精度 / 掩膜 / 全无效 / 波长口径 / 端到端），
其中波长口径用例还锁死了「2π 条纹 = 单程位移 λ/2」这个易错点，防止与 sbas 的口径漂移。

**仍然只能 Linux 的部分**：
- 整景或长时序（几十景 SBAS 反演）——精度和内存都不够，必须 snaphu + 大内存；
- Sentinel-1 干涉处理（isce2）——见下面第 3 条。

**如果要启用 snaphu**（按推荐顺序）：
1. 有 Linux 服务器时直接 `pip install snaphu`，`--backend auto` 会自动优先用它；
2. 本机 WSL：`wsl.exe` 仍被安全策略黑名单拦截，需在「安全中心 → 命令安全 → 程序黑名单」手动放行，
   再装 Ubuntu（本机与另一台机器都被这条策略挡着）。

### 2. 本机无 Docker / 无 C 编译器 / 无 WSL

排查结果（2026-10-30）：

| 环境 | 状态 |
|---|---|
| WSL | 被安全策略黑名单拦截（拒绝访问） |
| Docker | 无 |
| gcc / cc / cl（C 编译器） | 无 |
| cmake / make | 无 |
| MSYS / MinGW / Cygwin | 无 |

这些共同导致：**任何需要「编译 C/C++ 原生扩展」的遥感工具在本机都装不了**。
不仅 snaphu，未来若引入 ISCE2、MintPy 等 InSAR 处理引擎，同样要 Linux。

### 3. Sentinel-1 干涉处理需要 Linux + 大内存

要拿到 Sentinel-1 的 12 年形变时序（茜坑有 837 景 SLC，2014 至今），必须自己跑干涉
（isce2 / MintPy）。这套栈：
- 依赖 Linux（isce2 无 Windows 支持）；
- 内存要求高（处理整景 SLC，建议 ≥32GB；本机 i7-4790 / 16GB 不够）；
- 处理量大（数十景配准 + 干涉 + 解缠 + 时序反演，单矿区可能数小时到数天）。

**结论**：Sentinel-1 长时序 SBAS 是「有 Linux 服务器」之后的阶段，本机做不了。

## 二、数据瓶颈（数据本身还不够，不是代码问题）

### 4. NISAR 时序太短（3 个月），出不了可信加速度

实测（茜坑矿区，track 18，8 期，2026-06 ~ 2026-10）：

- **速率**：中位 -10.5 mm/yr，量级合理，但标准差 69 mm/yr，信噪比约 0.2 —— **勉强可用**；
- **加速度**：中位 -104 mm/yr²，标准差 1024 mm/yr²，**信噪比仅 0.10** —— **完全不可用**；
- 去平面后残差/原始 = 0.94，说明空间上几乎没有可分辨的形变结构，基本是噪声。

**根因**：加速度是位移的二阶导，噪声被平方级放大。3 个月、8 期数据，单期大气/轨道残差
（几十 mm）远超真实加速度信号（每月几 mm 的变化），无法靠时间平均压掉。

**结论**：要出可信加速度和「倒数速度外推失稳时刻」，需要：
- **≥1 年时序**（等 NISAR 数据积累——NASA 称 2026 年底补完 2025-09 以来的数据，约 14 个月）；
- 或换 **Sentinel-1 的 12 年时序**（但需先解决第二节的 Linux 处理能力）。

**代码的正确处理**：`algorithms/deformation.py` 对数据不足返回 `insufficient=True`，
`run_deformation.py` 会输出 `reliable:false` 并明确标注「信噪比 < 0.3，不输出加速度与失稳判定」。
**宁可说"数据不够"，不把噪声当形变**——这是口径红线，不能为了演示好看而编数。

### 5. NISAR 幅宽边缘导致覆盖率骤降

同一矿区、不同轨道，有效像元占比可差 6 倍：

| 轨道 | 方向 | 幅宽经度范围 | 茜坑（114.87~114.93）位置 | 有效率 |
|---|---|---|---|---|
| track 140 | 升轨 | 114.57~117.76E | 贴西边缘 | **14.3%** |
| track 18 | 降轨 | 113.84~117.12E | 居中 | **84.2%** |

**结论**：**选轨道比选日期重要**。GUNW 的幅宽边缘（near/far range 两端）有大量无效像元，
矿区若贴边，掩膜会把大部分像元置 0。检索时先看轨道足迹（`stringFootprint`），
选覆盖居中的轨道。

### 6. NISAR 下载体量（磁盘与时间成本）

- 单景 GUNW 2.2~2.3 GB（含 80m 解缠 + 20m wrapped 复数 + 元数据）；
- 本机走代理下载约 2.6 MB/s，单景约 11 分钟，8 期约 1.5 小时、约 18GB；
- 缓存落在 `inference/.cache/nisar/`，已 gitignore，不进仓库。

**结论**：批量下载前先确认磁盘（本机 E 盘 244GB 余量够），演示前可预下载"预热"。

### 7. Earthdata 账号的两次前置授权

NISAR 数据免费，但要 Earthdata 账号，且首次下载前有两道「人工」关卡（代码无法代劳）：

1. **档案补填 Study Area**：否则 ASF 返回 401「application required attributes: Study Area」，
   需到 `urs.earthdata.nasa.gov` 个人档案补填研究领域；
2. **应用预授权**：访问 ASF 给的 `approve_app?client_id=...` 链接点同意，
   否则 401「Pre authorization required」。

这两步做完才拿到下载凭证。凭据放 `~/.netrc`（机器 `urs.earthdata.nasa.gov`），不入仓库。

## 三、算法瓶颈（方法本身的性质，需正确预期）

### 8. 单轨只能给 LOS 视线向，不等于垂直沉降

InSAR 天然只能测「视线向（LOS）位移」。单条轨道的结果**不能写成"垂直沉降"**。
要解出垂直 + 东西向分量，需要升降轨联合（`algorithms/deformation_fusion.py` 的
`decompose_los_to_2d` 已实现）；南北向因轨道近极地，基本不可解。

**结论**：报告和界面必须标注「LOS 视线向」，升/降轨联合前不承诺"沉降量"。

### 9. 单期干涉图有长波大气/轨道残差，必须参考区归零

实测：单期位移整体偏移可达上百 mm（track 18 中位 +160mm，折算 4.9m/yr，物理上不可能）。
这是大气/轨道残差，不是真实形变。必须选「稳定参考区」把每景减去参考区中位值
（`algorithms/sbas.py` 的 `reference_correction`）。不做这步，速率场会整体偏一个假常数。

### 10. 加速度对噪声极其敏感，是「数据够多」才能做的指标

速度是一阶导（抗噪一些），加速度是二阶导（噪声放大）。这是数学性质，不是实现问题。
工程上的正确姿态是：**先看信噪比，达标才输出加速度**，否则明说"数据不足"。

## 四、口径红线（交付合规，任何时候不能越）

这些在 `docs/24` 和既有报告里已有，形变功能新增后补充两条：

1. **形变速率/加速度是「潜在形变风险筛查」，不是边坡稳定性评价，不给安全系数**。
2. **信噪比不足时，形变结果必须标注"仅供参考"，且不参与风险提级**——否则就是把噪声当
   滑坡信号，可能造成误报警或漏报，后果比"没数据"更严重。
3. 单轨结果是 LOS 视线向，非垂直沉降；判定需结合边坡单元、现场勘察与多源数据复核。

## 五、一句话总结瓶颈与下一步

| 瓶颈 | 性质 | 绕过/解决 |
|---|---|---|
| snaphu/isce3 无 Windows | 平台 | 20m 解缠放 Linux；80m 用官方已解缠产品 |
| 本机无 WSL/Docker/编译器 | 平台 | 开 WSL 或上 Linux 服务器 |
| Sentinel-1 干涉处理 | 平台 | 需要 Linux + 32GB 内存 |
| NISAR 时序仅 3 个月 | 数据 | 等积累到 1 年，或换 Sentinel-1 |
| NISAR 幅宽边缘 | 数据 | 选覆盖居中的轨道 |
| 单轨 LOS / 大气残差 | 算法 | 升降轨联合 + 参考区归零，标注口径 |

**当前状态**：A 阶段（80m SBAS + 速率场）本机可跑通；B 阶段（判定/融合/提级/报告）已进平台；
C 阶段（20m 解缠）代码就绪、待 Linux。**平台侧已具备完整的形变判定能力，只等数据积累或
Linux 环境到位，速率/加速度就能换成可信结果。**
