# 权限覆盖与项目隔离审计报告

> 审计日期：2026-10-22
> 触发问题：客户反馈「解译超时」「权限覆盖是否到位」「数据要按项目管理」
> 审计范围：`backend-java` 全部 27 个 Controller、103 个端点 + 前端 4 个核心数据页

---

## 一、审计方法

1. 静态扫描：遍历所有 `*Controller.java`，统计每个端点的
   - 是否声明 `Authentication` 参数（拿得到当前用户）
   - 是否调用 `guard.require(actionPerm)`（功能权限）
   - 是否调用 `guard.requireAccess(projectId, auth)` / `projectService.requireAccess(...)`（项目归属）
2. 动态验证：用 **`analyst` 账号**（**不是**项目 3 的成员）访问项目 3 的各类接口，
   期望全部 403；再访问自己所属的项目 1，期望 200。

> 静态扫描会误报——例如 `service.get(id, username, isAdmin)` 把校验下沉到 Service 层，
> 或 `AuthController.login` 本就不需要权限。所以每一条都做了人工复核。

## 二、发现并修复的真实漏洞（3 处）

### 漏洞 1：传感器数据跨项目越权（高危）

**位置**：`sensor/SensorController.java` 全部 4 个端点

**问题**：
```java
@GetMapping
public ApiResponse<List<Sensor>> list(@RequestParam(required = false) Long projectId) {
    return ApiResponse.ok(sensorService.list(projectId));   // 无 auth、无校验
}
```
- 方法签名里**没有 Authentication**，Service 层也无从校验
- `projectId` 可不传 → 返回全部项目的传感器
- `/{id}/data`、`/{id}/displacement`、`/{id}/export` 只要知道传感器 id 就能读数据、导出 CSV

**影响**：任何登录用户可读取任意矿区的 GNSS 位移、雨量、土壤含水率数据，
**位移数据是判断边坡是否滑动的前兆指标**，泄露后果严重。

**修复**：
- 注入 `PermissionGuard`
- `list` 的 `projectId` 改为**必填**并 `guard.requireAccess`
- 其余 3 个端点新增 `requireSensorAccess(sensorId, auth)`：
  先按 id 取传感器，再用它的 `projectId` 校验成员身份

### 漏洞 2：全局搜索跨项目泄露（中高危）

**位置**：`search/SearchController.java`

**问题**：直接 `projectRepo.findAll()` / `imageryRepo.findAll()` /
`extractionRepo.findAll()` / `alarmRepo.findAll()` 全表扫描后按关键词匹配，
完全不看当前用户能访问哪些项目。

**影响**：普通用户搜索「Pilgangoora」能搜出别人项目的名称、影像名、解译记录名、告警，
等于一份跨项目资产清单。

**修复**：
- 加 `Authentication` 参数
- 先算 `projectService.listForUser(username, isAdmin)` 得到可见项目 id 集合
- 四类数据全部按 `visible.contains(projectId)` 过滤；可见集合为空直接返回空

### 漏洞 3：大屏汇总无归属校验（中危）

**位置**：`screen/ScreenController.java` `GET /api/screen/summary`

**问题**：`projectService.get(projectId)` 不带用户，任何登录用户传任意 projectId
都能拿到该矿区的名称、地址、联系方式、在线设备数、今日告警数、解译面积。

**修复**：新增 `Authentication` 参数 + `projectService.requireAccess(projectId, username, isAdmin)`。

## 五、项目隔离机制（数据怎么分项目）

### 数据模型

所有业务数据表都带 `project_id`：

```
projects (项目)
  ├── project_members (成员：project_id + username)
  ├── imagery          (影像)
  ├── aoi_boundary     (边界，含 PERMIT/DISTURBANCE/ECO 三类)
  ├── extractions      (解译记录)
  ├── aoi_watch        (关注区)
  ├── stations/sensors (站点与传感器)
  ├── alarms           (告警)
  ├── warning_rules    (预警规则)
  └── share_links      (访客分享)
```

### 访问控制三层

1. **登录态**：无 token → 401（Spring Security 统一拦截）
2. **功能权限**：`guard.require("action:xxx")` 按角色权限点判断（动态 RBAC）
3. **项目归属**：`guard.requireAccess(projectId, auth)` 判断是否项目成员
   - 管理员（ADMIN 角色）放行全部
   - 普通用户只放行 `project_members` 里有的项目

### 前端配合

- 顶部项目选择器决定 `projectStore.currentId`
- 影像库/边界/解译/分析页全部把 `projectId` 传给后端
- **本轮补强**：影像库原先传 `projectId: currentId ?? undefined`，
  未选项目时后端会返回「当前用户可见的全部项目」的影像，跨项目混在一张列表里。
  现改为**未选项目时不发请求**，页面顶部显示醒目提示并提供「去项目管理」按钮。

## 六、新建项目功能设计（本轮新增）

### 为什么需要扩充

原来只有 5 个通用字段（名称、区域、状态、负责人、说明），
不足以支撑矿山业务——报告要写矿权证号、越界分析要矿权面积作基准、
地图要能定位到矿区中心。

### 字段设计（分三组）

**基本信息**
- 项目名称（必填）
- 所在区域
- 项目状态（进行中 / 规划中 / 已归档）

**矿权与开采**
- 矿种（锂矿/铁矿/铜矿/石灰岩/煤矿，可自定义输入）
- 采矿许可证号（报告合规章节引用）
- 矿权面积 km²（**越界分析的对比基准**）
- 开采方式（露天 / 井下 / 联合）

**对接与坐标**
- 内部负责人（我方）
- 客户对接人 + 联系方式
- 矿区中心点（经/纬）+「从边界取中心」一键计算
- 坐标系（EPSG:4326 / 4490 / 4547）
- 项目说明

### 交互设计

1. **新建后自动切换**：创建成功立刻 `projectStore.set(created.id)`，
   避免用户建完还在旧项目里操作，把数据挂错项目
2. **从边界取中心**：读取项目已导入的矿权/扰动边界，算环的几何中心填入经纬度
3. **对话框顶部说明**：新建时提示「项目是所有数据的归属单元，只有项目成员可见」
4. **后端表结构**：`projects` 表由 JPA `ddl-auto=update` 自动补 9 列，已有数据保持 null

### 数据库变更（已自动完成）

```

license_area_km2   double
mining_method      varchar(32)
center_lng         double
center_lat         double
```

## 七、解译超时问题（同批修复）

### 问题

本地解译页提取水体后报「解译超时」。查 `ExtractView.vue`：

```js
async function pollUntilDone(taskId, maxTicks = 60) {   // ← 只等 60 秒
  for (let i = 0; i < maxTicks; i++) { ... }
  throw new Error('解译超时，请检查解译服务日志')
}
```

高分影像（数百 MB GeoTIFF）读全波段 + 阈值分割 + 多边形矢量化，
60 秒根本不够；且原实现**没有调用 inference 的任务状态接口**，
只是盲查数据库，任务失败也拿不到原因。

### 修复

1. 轮询先查 `GET /api/v1/inference/{taskId}/status` 拿真实状态与进度
2. `FAILED` 时直接把 inference 的 `error` 抛给用户（不用再翻服务日志）
3. 任务 `SUCCESS/EMPTY` 后再等 Java 回调落库（两者之间有延迟）
4. 超时上限 60 秒 → **600 秒**
5. 每 5 秒在界面显示「正在解译…已等待 N 秒」，避免用户以为卡死

## 八、附带修复：refresh 401 反复出现

**现象**：控制台反复报 `api/auth/refresh 401`。

**根因**：`/api/auth/refresh` 失败时返回值里没有清 `rs_session` cookie。
前端 `hasSessionMarker()` 看到标记还在，下次页面加载又探测一次 → 再 401。

**修复**：refresh 失败返回 401 的同时，`Set-Cookie` 清掉 `rs_session` 与 `refresh_token`
（`Max-Age=0`）。前端拿到 401 后跳登录页，不再重复探测。
