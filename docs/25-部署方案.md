# 部署方案（落地 / 交付）

> 时间：2026-10-30
> 适用范围：三个应用服务（frontend / backend-java / inference）+ 数据层（MySQL，PostGIS 预留）
> 结论先行：**推荐 Linux + Docker Compose 单机**；客户不给 Docker 就走 systemd 裸机；两种都用同一份 nginx 配置和同一套环境变量。

---

## 一、先认清这套系统由什么组成

| 组件 | 形态 | 对外端口 | 谁来访问 |
|---|---|---|---|
| frontend | 静态文件（Vite 构建，17MB，含 Cesium 资源） | 80 / 443 | 浏览器 |
| backend-java | Spring Boot 3 fat jar | 8080（**仅内网**） | nginx 反代 |
| inference | FastAPI + uvicorn | 8010（**仅内网**） | nginx 反代 + Java 直连 |
| MySQL 8 | 业务库 | 3306（**仅内网**） | backend |
| Redis / EMQX / MinIO | 已编排、**代码尚未接入** | — | 暂不启用 |

关键点：**只有 nginx（80/443）对外**。8080 / 8010 / 3306 一律不映射到宿主机，
排查时用 `docker compose exec` 或临时加端口，不要图省事长期暴露。

调用关系（部署时最容易错的地方）：

```
浏览器 ──/api/*──▶ nginx ──┬─▶ backend(8080)
       ──/sentinel/*─┘      └─▶ inference(8010)   ← nginx 剥掉 /sentinel 前缀
backend ──HTTP──▶ inference（提交解译）
inference ──回调──▶ backend  ← 地址由 JAVA_CALLBACK_URL 决定，见第四节
```

## 二、三档部署形态，按客户现场选

| 档位 | 适用 | 优点 | 代价 |
|---|---|---|---|
| **A. Docker Compose 单机**（推荐） | 试点、客户内网 Linux 服务器 | 一条命令起停、依赖不污染系统、升级换镜像即可回滚 | 需要装 Docker；镜像要能带进内网 |
| **B. systemd 裸机** | 客户禁止容器 / 老旧服务器 | 无额外依赖，运维熟悉 | 环境靠人守（JDK17、Python3.11+、GDAL 相关轮子），升级要手工换 jar/代码 |
| **C. K8s / 多机** | 多矿区、对外服务 | 可横向扩 | 现在没必要：**inference 的任务表在进程内存里，多副本会分裂**，得先改 Redis |

现在这个阶段（一两个矿区、单机几十个用户）走 **A**，把 B 作为退路。C 等任务表外置之后再说。

## 三、A 档：Docker Compose 单机（默认方案）

产物都在 `deploy/prod/`：

```
deploy/prod/
├── docker-compose.yml          全栈编排（mysql + backend + inference + frontend）
├── .env.example                所有可变项（密码、密钥、端口）
├── nginx/rs-platform.conf      /api 与 /sentinel 反代、2GB 上传、SPA 回退
├── docker/
│   ├── Dockerfile.backend      maven 多阶段构建 → temurin 17 JRE
│   ├── Dockerfile.inference    python:3.13-slim + libgomp1（sklearn 需要）
│   └── Dockerfile.frontend     node 构建 → nginx:alpine
├── systemd/                    B 档用：rs-backend.service / rs-inference.service
└── scripts/
    ├── smoke.sh                起来后逐项验活（三条健康检查 + 登录 + 业务接口）
    └── backup.sh               MySQL 逻辑备份 + 影像目录打包，按天保留
```

### 3.1 部署步骤（概要）

```bash
# 1. 准备（宿主机只需 Docker + compose 插件）
git clone <repo> /opt/rs-platform && cd /opt/rs-platform

# 2. 配环境变量（务必改密码与密钥，见第四节）
cd deploy/prod && cp .env.example .env && vi .env
#    JWT_SECRET / INFERENCE_CALLBACK_TOKEN 用 openssl rand -base64 48 生成

# 3. 构建 + 启动（首次约 10–20 分钟，主要是 maven 与 pip 拉包）
docker compose --env-file .env up -d --build

# 4. 验活
./scripts/smoke.sh

# 5. 浏览器打开 http://<服务器IP>/ ，admin / admin123，**立即改密码**
```

日常运维就四条：

```bash
docker compose ps                 # 看状态（healthcheck 结果直接可见）
docker compose logs -f backend    # 跟日志
docker compose restart inference  # 重启单个服务
docker compose down               # 停（数据在命名卷里，不会丢）
```

### 3.2 目录与卷

| 卷 | 挂载点 | 内容 | 要不要备份 |
|---|---|---|---|
| `rs-mysql` | `/var/lib/mysql` | 业务库（用户/项目/解译记录/告警） | **要** |
| `rs-imagery` | `/data/imagery` | 上传的原始影像（100MB–800MB/景） | **要**（或客户自有备份） |
| `rs-cache` | `/data/cache` | Sentinel-2 / DEM 瓦片缓存 | 不用（可重下） |
| `rs-demo` | `/data/demo` | 离线演示数据包 | 建议留（内网重下不了） |

`rs-imagery` 是后端 `app.imagery.upload-dir` 指过去的，**默认值是 `./data/imagery`（相对工作目录）**，
容器里必须用环境变量改成绝对路径 `/data/imagery`，否则重启后文件散落在容器内、`down` 一次就没了。

## 四、三个必须改的配置（改错会静默失效，不报错）

这是这套系统部署时最容易翻车的三处，全部属于"不报错、但结果不对"：

**1. `JAVA_CALLBACK_URL`（容器化必改）**

```yaml
JAVA_CALLBACK_URL=http://backend:8080/api/callback/task-complete
```

代码默认值是 `http://localhost:8080/...`。在容器里 `localhost` 指的是 inference 容器自己，
于是**回调打到不存在的 8080，解译结果永远落不了库，前端一直"进行中"**，日志里只有一条回调失败。
裸机部署（B 档）时 backend 与 inference 同机，这个默认值反而能用——两档的差异主要就在这里。

**2. `INFERENCE_CALLBACK_TOKEN`**

必须与 Java 侧完全一致，且**上线前换成随机串**（默认值是仓库里公开的 demo 串）。
不带或不对，后端回调入口直接 401；这个端点历史上裸奔过，能被匿名写假数据。

**3. `JWT_SECRET`**

默认值是 `dev-only-secret-...`，公开可见。上线必须注入 ≥32 字节随机值，
否则任何人都能自己签一个管理员令牌。

## 五、B 档：systemd 裸机

宿主机需要：JDK 17、Python 3.11+（带 venv）、MySQL 8、nginx。
产物：`deploy/prod/systemd/rs-backend.service`、`rs-inference.service`。

```
/opt/rs-platform/
├── backend.jar                 # mvn package 产物
├── inference/                  # 整个目录（含 .venv）
├── web/                        # 前端 dist 内容
└── data/imagery/               # 影像
/etc/rs-platform/
├── backend.env                 # 环境变量（同 .env，权限 600）
└── inference.env
```

```bash
useradd -r -s /sbin/nologin rs
systemctl daemon-reload
systemctl enable --now rs-backend rs-inference
systemctl status rs-backend
```

nginx 用同一份 `rs-platform.conf`，只把 upstream 从 `backend:8080` 改成 `127.0.0.1:8080`、
`inference:8010` 改成 `127.0.0.1:8010`，`root` 指到 `/opt/rs-platform/web`。

**Windows 服务器**（客户只给 Windows）：用 WinSW 把两个 jar/py 包成服务，本质与 systemd 相同。
需要的话我按 WinSW 的 xml 再出一版。

## 六、外网依赖：内网部署的真正难点

inference 是**唯一需要出网**的组件，它要访问：

| 依赖 | 用途 | 内网影响 |
|---|---|---|
| AWS Earth Search STAC + S3（COG） | 在线 Sentinel-2 检索与拉波段 | 断网 → 在线解译、预览、RSEI、DEM 全不可用 |
| AWS Terrarium DEM | 坡度/边坡/风险评估 | 同上 |
| Copernicus（已弃用） | — | 无需关心 |

所以**内网部署必须先决定走哪条路**：

**路线 1（推荐，也是客户生产的主路径）：本地高分影像**
客户买/已有的 GF-2、GF-7、无人机影像走「本地解译 + 本地监督分类」，全程不出网。
0.5m 分辨率比 Sentinel-2 的 10m 好看 20 倍，演示效果和报告可信度都更高。
这条路不依赖任何外网，部署完就能用。

**路线 2：预置离线演示包**
在能出网的机器上跑一次 `/api/v1/sentinel/demo-bundle`（把某矿区七类结果全算好落盘），
把 `demo_data/*.json` 拷进内网的 `rs-demo` 卷。前端「载入演示数据」直接读本地，断网秒出图。

**路线 3：预热瓦片缓存**
`.cache/`（本机已 150MB+）整体拷进 `rs-cache` 卷。同一景同一 tile 不再下载，
但**换矿区/换日期仍需要外网**，只能救急不能当方案。

**如果要长期在内网用 Sentinel-2 时序**：得在客户内网搭本地镜像（自建 STAC 或定期同步
Copernicus 数据到 MinIO + 改 `algorithms/sentinel.py` 的 endpoint）。这是个独立工作量，
不建议在第一期做。

> 交付话术要统一：**「平台支持在线 Sentinel-2，也支持本地高分影像；内网环境以本地影像为主，
> 在线能力按需开通。」** 别承诺内网也能随便拉最新 Sentinel 影像。

## 七、容量规划（一个矿区，5 年数据）

| 项 | 估算 | 说明 |
|---|---|---|
| CPU | 8 核起 | 随机森林分类、RSEI 的 PCA、融合栅格化都是 CPU 密集 |
| 内存 | 16GB | inference 峰值：4096² 栅格 × 7 维 float32 ≈ 470MB，再加 RF 与中间数组 |
| 影像盘 | 2TB | 按 180 景 × 300MB ≈ 54GB 原始 + 结果与缓存；留足余量给后续矿区 |
| 系统盘 | 100GB | 镜像（backend ~250MB、inference ~1.2GB、frontend ~60MB）+ 日志 |
| 数据库 | < 5GB | 业务数据是元数据与矢量 JSON，量很小 |

## 八、加固清单（上线前逐条过）

1. 只暴露 80/443；`docker compose ps` 里不应看到 8080/8010/3306 的 `0.0.0.0:` 映射
2. 三个密钥全部改掉（第四节）
3. **改掉 admin 默认密码**，并按项目建账号、按角色授权（权限体系已细化到 28 页面 / 18 操作）
4. HTTPS：内网可用客户证书或自签；`server_name` 改成实际域名/IP
5. 上传目录不可被直接下载（nginx 只 serve `/assets`、`/cesium` 与 SPA 回退，别把 `/data` 加进 root）
6. 备份任务加进 crontab，并**做过一次恢复演练**（没演练过的备份等于没有）
7. 日志：`docker compose logs` 默认 json-file 会吃盘，给 backend/inference 配 `logging.options.max-size`
8. 时间同步（chrony/ntpd），否则 JWT 过期时间与告警时间会漂

## 九、升级与回滚

```bash
# 升级前：备份（数据库 + 影像目录）
./scripts/backup.sh

# 拉新代码 → 重新构建 → 只重启变化的服务
git pull && docker compose --env-file .env up -d --build backend inference frontend

# 回滚：镜像 tag 回到上一版（所以**不要用 latest**，用版本号或 git sha）
docker compose --env-file .env up -d backend=registry/backend:1.4.2
```

三个约束：

1. **数据库迁移要能回滚**。现在 `spring.jpa.hibernate.ddl-auto: update`（自动加表加列，不会删），
   demo 期够用；正式交付前应切到 **Flyway**，每次变更一个可回滚脚本。
2. **升级时别在跑解译任务**。任务表在进程内存里，重启即丢，正在算的单子要重提。
3. **inference 必须单副本、单 worker**。uvicorn 多 worker 或多容器都会让任务表分裂——
   提交落在 A 进程、查进度打到 B 进程，表现为"任务不存在"。要扩就先把任务表换 Redis。

## 十、上线检查清单

部署当天照着勾，勾完再交给客户：

- [ ] `docker compose ps` 四个服务都 `healthy`
- [ ] `scripts/smoke.sh` 全绿（三条健康检查 + 登录 + 影像列表 + 解译提交一次）
- [ ] 浏览器硬刷后：登录、切项目、大屏出图、影像库列表有数据
- [ ] 上传一张真实 GeoTIFF（≥100MB），确认 2GB 上限与 nginx 不截断
- [ ] 跑一次本地监督分类，拿到 OA/Kappa，结果能落到解译记录
- [ ] 跑一次解译提交 → 等回调 → 记录里出现结果（验证 `JAVA_CALLBACK_URL` 那条）
- [ ] 生成一份 Word 报告，确认第九章附录里有解译明细
- [ ] `backup.sh` 手工跑一遍，恢复到临时库验证能查
- [ ] 断网演练：拔掉外网，确认本地影像链路仍可用、在线解译给出明确报错而不是卡死
- [ ] 记下三个密钥的存放位置（交付文档里不要写明文）

## 十一、还没做、但交付前该补的

1. **MinIO 没接**：现在影像存本地磁盘，compose 里虽然编排了 MinIO 但后端没有客户端代码。
   单机部署用本地卷没问题；要上多机或做对象存储再接入。
2. **没有 CI**：目前靠本地 `mvn package` / `npm run build` / `pytest`。建议至少加一条
   "构建 + 三条健康检查"的流水线，避免把没编译过的包带上线。
3. **没有监控**：只有 compose healthcheck。客户要求 SLA 的话，加 Prometheus + Grafana，
   backend 已引 actuator，inference 有 `/health`，起步成本很低。
4. **日志没有集中收集**：排查要靠 `docker compose logs`。多机时再上 Loki/ELK。
