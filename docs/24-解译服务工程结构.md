# 解译服务（inference）工程结构重构

> 时间：2026-10-30
> 范围：`inference/` 目录整体重排；**不改任何接口路径、请求体、响应结构**
> 验证：重构前后 OpenAPI 对比，27 条路径 / 28 个方法 / 26 个 schema 完全一致

## 一、为什么要动

功能是一路加出来的，能用，但越来越难维护。具体症状：

1. **`main.py` 1488 行**：28 个端点、26 个 Pydantic 模型、后台线程、回调、算法调用全在一个文件里。
   改一个端点要在 1500 行里上下找，同一个文件里既有 HTTP 逻辑也有算法编排。
2. **模块 import 藏在文件中间**：`import sentinel as aws_sentinel  # noqa: E402` 这类语句
   散在十几个位置（`# noqa: E402` 本身就是"import 位置不规范"的标记）。
3. **22 个 `patch_xxx.py` / `fix_upload.py`**：靠"写脚本改脚本"推进，补丁执行完就留在目录里，
   既不知道哪些已生效，也不知道改了哪些地方。
4. **算法、测试、一次性排查脚本混在一层**：16 个算法模块 + 7 个 `selftest_*.py` +
   2 个 `probe_*.py` 全平铺在 `inference/` 下，看不出哪个是产品代码。
5. **硬编码了另一台机器的绝对路径**：`C:/Users/asus/Desktop/尚子安/...` 出现 3 处，
   换机器直接跑不起来。
6. **函数内重复 import**：`import base64` 在 5 个函数里各写一遍，`import os as _os` 出现 3 处。
7. **`__import__("math")`**：明明文件头已 `import math`，某次补丁却用 `__import__` 绕路，
   还把三重括号的面积公式塞进 return 字典。

结论：不是"能不能跑"的问题，是"别人接手要多久看懂"的问题。

## 二、重构后的结构

```
inference/
├── main.py                  3 行，只有 app = create_app()
├── app/                     应用层（HTTP 相关）
│   ├── __init__.py          create_app()：中间件 + 路由 + 生命周期
│   ├── config.py            环境变量与常量集中处
│   ├── logging_setup.py     日志格式（原来全是 print）
│   ├── middleware.py        请求 ID + 耗时日志
│   ├── tasks.py             任务表 + 回调 Java
│   ├── geo.py               AOI → 外接矩形 / 面积
│   ├── schemas.py           跨路由共用模型
│   └── routers/             14 个文件，一个 URL 前缀一个
├── algorithms/              算法层（纯计算，不 import fastapi）
│   ├── paths.py             缓存目录常量
│   └── 15 个算法模块
├── tests/                   pytest：契约 + 离线业务链路
├── scripts/
│   ├── selftest/            需要真服务/真网络的端到端自检
│   └── probe_*.py           数据源调研脚本（可选依赖）
├── requirements.txt         运行依赖（锁版本，补上漏掉的 Pillow/affine）
├── requirements-dev.txt     pytest
├── pyproject.toml           pytest / ruff 配置
├── .env.example             环境变量模板
└── README.md                结构说明 + 启动 + 排障
```

分层规则（写在 README 里，改代码前先看）：

1. routers 不写业务逻辑，只解析请求、调算法、拼响应；
2. algorithms 不依赖 FastAPI，能被脚本和测试直接调用；
3. 跨包引用一律相对导入（`from . import dem`），整包可搬；
4. 新增 URL 前缀 = 新建一个 router 文件 + 在 `routers/__init__.py` 登记。

## 三、几个具体决策

**为什么算法层要跟 FastAPI 解耦**：算法现在可以被 `tests/`、`scripts/selftest/`、
notebook 直接调，不用起服务。以前 `main.py` 里的编排逻辑无法单测，这也是当初只能写
`selftest_*.py` 打真实接口的原因。

**为什么一个前缀一个文件**：`/api/v1/risk` → `risk.py`，URL 和文件一一对应，
出新问题时按 URL 就能定位文件，不用在 1500 行里搜。

**为什么抽 `tasks.py`**：任务表 + 回调以前匿名嵌在 `main.py`，两份提交逻辑（上传解译、
在线解译）各写一遍 `with _lock: _tasks[...] = ...; threading.Thread(...)`。
抽出来后统一 `submit_task(fn, payload)`，未来换 Celery 只改这一个文件。

**为什么加请求日志中间件**：解译接口动辄几十秒，出问题要能看出"哪个请求、多久、
什么状态"。现在每个请求有 `X-Request-ID`，日志行形如：

```
2026-10-30 09:48:01 INFO  [request] GET /api/v1/imagery/inspect -> 200 耗时=1031ms req=d686daaef599
```

## 四、顺带修掉的 5 个真实缺陷

这些都不是"风格问题"，是会真的出错：

1. **报告附录永远是空的**。`ReportRequest` 模型漏声明 `extractions` 字段，
   前端和 Java 都在传，Pydantic 静默丢弃 → 第九章"解译成果明细"永远显示"暂无记录"。
   代码里还留着一句注释提醒过这个坑（"漏写会导致章节静默消失"），结果自己踩了。
2. **`requirements.txt` 漏了 Pillow**。PIL 用了 14 处（预览图、坡度图、融合图、分类图），
   全新环境装完要到出图时才 `ModuleNotFoundError`。同时补声明 `affine`（直接 import 了它）。
3. **`affine 3.0` 弃用 `*` 做矩阵乘法**。`supervised_local.py` 两处会在未来版本失效，
   改为 `@`。
4. **搬迁后瓦片缓存路径会变**。`sentinel.py` 原来用 `__file__` 现算 `.cache`，
   挪进 `algorithms/` 后缓存会落到包内部、150MB 预热瓦片全废。改为集中读
   `algorithms/paths.py` 的 `CACHE_DIR`，并保持 `<md5>/` 的原有布局不变。
5. **3 处硬编码另一台机器的绝对路径**（`C:/Users/asus/...`），改成
   `$RS_TEST_TIF` + 仓库相对路径，换机器不再断。

## 六、还没做的（按价值排序）

1. **统一错误处理**：现在每个端点手写 `try/except → HTTPException`，
   可以加一层 exception handler 把 `ValueError → 400`、其余 → 500 + 统一 body。
   没顺手改是因为它会改变响应体形状，属于对外契约变更，要先跟 Java 侧对齐。
2. **`sample_sets` 表**：样本集入库、跨机器复用（docs/19 的 P1）。
3. **`demo_data/` 进 .gitignore**：演示包可能上百 MB，目前靠 `.gitignore` 里的
   `inference/demo_data/` 兜着，规则没写在段首容易漏看。
4. **算法层的参数说明**：15 个模块的入参仍是 dict，没有类型定义；
   想做的话按模块补 TypedDict，路由层能少一次手工取值。
